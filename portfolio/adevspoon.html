하루 한 번의 발급을 지키는 동시성 제어

문제동시 요청으로 사용자별 하루 1회 질문 발급 정책이 깨질 수 있었습니다.

판단 근거

발급 여부를 판단하는 전체 과정이
사용자 단위 임계구역이었습니다.

  • 보호 범위: 질문 선택, 발급 이력 저장, 발급 카운트 증가까지 함께 보호해야 했습니다.
  • 락 범위: 같은 사용자만 순차 처리하는 Named Lock을 선택해 다른 사용자의 발급은 분리했습니다.
  • 실행 순서: Lock AOP가 트랜잭션보다 먼저 실행되도록 설정하고, 락 획득 후 최신 이력을 다시 조회했습니다.
Serializable · 비관적 락 · UNIQUE를 비교한 이유
선택지이 요구에서의 판단
Serializable격리 수준을 높이면 경합과 재시도 비용까지 고려해야 합니다.
비관적 락미발급 이력은 잠글 행이 없습니다. 사용자 행을 잠그는 대안은 가능하지만 관련 작업의 경합 범위도 검토해야 합니다.
UNIQUE중복 저장의 최종 방어선입니다. 발급 판단 전체를 순차 처리하는 역할은 별도로 필요했습니다.
Named Lock · 선택발급 이력 유무와 관계없이 사용자 키로 전체 흐름을 보호할 수 있었습니다.

핵심 코드

Kotlin · 핵심 발췌
{% highlight kotlin %} // @Order(1)인 DistributedLockAdvisor의 메서드 fun atTarget(joinPoint: ProceedingJoinPoint): Any? { val lockAnnotation = getAnnotation(joinPoint) val lockKeyList = getLockKeyList(joinPoint.args, lockAnnotation.keyClass) return lockRepository.withAllLock(lockKeyList) { joinPoint.proceed() } } @Transactional @DistributedLock(keyClass = [GetTodayQuestion::class]) fun getOrCreateTodayQuestion(request: GetTodayQuestion): QuestionInfo { val user = getMember(request.memberId) val latestIssuedQuestion = questionOpenRepository.findLatestWithQuestionAndAnswer(user) val isTodayQuestion = latestIssuedQuestion?.openDate?.isToday() ?: false return if (isTodayQuestion) makeQuestionInfo(latestIssuedQuestion!!) else questionOpenDomainService.issueQuestion(request.memberId, request.today) } {% endhighlight %}

Advisor와 서비스의 핵심 부분 발췌. Advisor의 @Around는 생략했습니다. 트랜잭션 AOP 순서는 LOWEST_PRECEDENCE - 10으로 설정했습니다.

02 / RELIABILITY · Transactional Outbox, Scheduler

누락된 신고 알림을 복구 가능한 작업으로

문제운영 중 신고 데이터는 저장됐지만 Slack 알림이 누락되는 사례가 발생했습니다.

{% include portfolio/report-notification.html %}

원인과 판단 근거

실패를 감지하는 것과
작업을 잃지 않는 것은 별개의 문제였습니다.

  • 원인 확인: 리스너 미실행·예외 은폐·외부 API 실패로 가설을 나눠 검증한 결과, Slack의 HTTP 오류 응답(4xx·5xx)을 검사하지 않아 실패를 감지하지 못했습니다.
  • 구조적 한계: 전송 작업이 메모리에만 존재해 외부 API 장애나 서버 재시작 시 미완료 작업을 복구할 수 없었습니다.
  • 동일 트랜잭션 저장: AOP 실행 순서를 조정해 신고 데이터와 Outbox를 같은 트랜잭션에 저장하고, 전송만 커밋 이후로 미뤘습니다.
  • 중복 선점 방지: 조건부 UPDATE와 행 잠금으로 다중 인스턴스가 같은 작업을 동시에 처리하지 않게 했습니다.
재처리 조건과 횟수 기준

스케줄러는 1분 간격으로 재처리 대상을 조회합니다. 최초 전송을 포함해 최대 4회 시도하며, 실패 후 다음 시도는 1분·5분·15분 뒤입니다. 408·429·5xx는 재시도하고 429 응답의 Retry-After는 다음 시도 시각에 반영합니다. 그 외 4xx는 재시도해도 같은 결과이므로 즉시 최종 실패로 처리합니다.

핵심 코드

Kotlin · 발췌
{% highlight kotlin %} // 신고를 저장하는 @Transactional 메서드 안에서 실행되는 AOP private fun bugReportEventPublish(result: Any?) { val event = (result as? ReportEvent) ?: throw ReportEventInvalidReturnException() val outbox = reportOutboxService.createPending( report = event.report, slackPayload = objectMapper.writeValueAsString(event.toSpecificMap()) ) eventPublisher.publishEvent(ReportOutboxCreatedEvent(outbox.id)) } // 커밋 이후 최초 전송. 스케줄러 재처리도 같은 attemptSend를 거친다. @Async @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) fun sendReportAlarm(event: ReportOutboxCreatedEvent) { reportOutboxService.attemptSend(event.reportOutboxId) } {% endhighlight %}

예외 로깅은 생략했습니다. attemptSend는 조건부 UPDATE로 작업을 선점한 뒤 전송하고, 결과(성공·재시도 예정·최종 실패)를 같은 트랜잭션에서 기록합니다.

검증 결과

22개단위·HTTP·통합 테스트 통과
8개 스레드동시 처리 시 단일 발송 검증
최대 4회최초 전송 포함 자동 재처리 한도

MockWebServer로 HTTP 500·404 응답을 재현해 기존 코드의 오류 감지 누락을 확인했고, 같은 시나리오로 개선 후 동작을 비교했습니다.

한계 · 다음 단계

전송 도중 서버가 종료되면 트랜잭션이 롤백되어 다음 주기에 다시 시도되므로(at-least-once), 전송 성공 직후 장애가 나면 같은 알림이 중복될 수 있습니다. 또한 Slack 응답을 기다리는 동안 DB 커넥션과 해당 행의 잠금을 점유합니다. 신고 알림은 발생 빈도가 낮아 이 비용을 감수했습니다.
