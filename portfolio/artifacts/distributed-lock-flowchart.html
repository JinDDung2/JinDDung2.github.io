분산 락 & 트랜잭션 플로우

tryLock(wait 3s, lease 5s) 기반 재고 차감 요청이 락 획득 성공/실패에 따라 어떻게 갈라지는지, 그리고 트랜잭션 커밋과 락 해제 순서를 어떻게 지켰는지 정리했다.

대기 시간 (waitTime)
최대 3초
임대 시간 (leaseTime)
자동 해제 5초
락 해제 시점
커밋 완료 이후

즉시 실패 (Fast Fail)
핵심 원칙

락 해제는 반드시 DB 트랜잭션 커밋이 끝난 뒤, finally 블록에서 이루어져야 한다.

  • 문제: @Transactional 메서드 안에서 tryLock()과 unlock()을 직접 실행하면, 락이 풀린 직후 아직 커밋되지 않은 짧은 순간 다른 스레드가 변경 전 데이터를 읽는 문제가 생긴다.
  • 해결: Facade가 락의 획득·해제 경계를 갖고, Service는 Propagation.REQUIRES_NEW로 별도 트랜잭션 경계를 가져 — 커밋이 끝난 뒤에만 락이 풀리도록 순서를 강제한다.

waitTime · 3초

락을 얻기 위해 대기하는 최대 시간. 이전 트랜잭션이 3초 안에 끝나 락이 풀리면 즉시 획득하고, 지나면 예외를 던져 과부하를 막는다.

leaseTime · 5초

락을 획득한 뒤 보유할 수 있는 최대 시간. 장애로 unlock()이 호출되지 않아도 5초 뒤 Redis가 자동으로 락을 삭제해 데드락을 막는다.

REQUIRES_NEW

Facade의 락 범위와 Service의 트랜잭션 범위를 분리하는 전파 옵션. 락이 풀리기 전에 커밋이 끝나도록 순서를 보장한다.

읽는 법

점선 화살표는 성공/실패 여부를 알리는 반환 흐름이다. ALT 박스는 tryLock 결과에 따라 갈라지는 두 경로를 보여준다 — 위 칸은 3초 초과로 즉시 실패하는 경로, 아래 칸은 락을 획득해 트랜잭션을 완료하고 락을 해제하는 경로다. 락 해제(⑤)는 항상 커밋(④) 다음에 일어난다.

구현 코드

StockRedissonFacade & StockService

락 획득·해제는 Facade가, 트랜잭션 경계는 Service가 나눠 가져 — 커밋이 끝난 뒤에만 락이 풀리도록 강제한다.

StockRedissonFacade.java · StockService.javaJava
// 1. Redisson Facade 클래스 (락 경계 설정 - @Transactional 없음)
@Component
@RequiredArgsConstructor
@Slf4j
public class StockRedissonFacade {

    private final RedissonClient redissonClient;
    private final StockService stockService;

    public void deductStock(Long stockId, Long quantity) {
        RLock lock = redissonClient.getLock("stock:lock:" + stockId);

        try {
            // tryLock(대기 3초, 임대 5초) - 실패 시 false 반환 (Fast Fail)
            boolean available = lock.tryLock(3, 5, TimeUnit.SECONDS);

            if (!available) {
                log.warn("락 획득 타임아웃 발생 - StockId: {}", stockId);
                throw new CustomException(ErrorCode.LOCK_ACQUISITION_TIMEOUT);
            }

            // 락 획득 성공 후, 별도 트랜잭션 서비스를 호출해 재고확인·차감·커밋 수행
            stockService.deductStockWithTransaction(stockId, quantity);

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new CustomException(ErrorCode.INTERNAL_SERVER_ERROR);
        } finally {
            // DB 트랜잭션이 완전히 커밋된 후 finally 블록에서 안전하게 락 해제
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
                log.info("분산 락 해제 완료 - StockId: {}", stockId);
            }
        }
    }
}

// 2. 비즈니스 트랜잭션 서비스 (REQUIRES_NEW 트랜잭션 분리)
@Service
@RequiredArgsConstructor
public class StockService {

    private final StockRepository stockRepository;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void deductStockWithTransaction(Long stockId, Long quantity) {
        Stock stock = stockRepository.findById(stockId)
                .orElseThrow(() -> new CustomException(ErrorCode.STOCK_NOT_FOUND));

        stock.deduct(quantity);
        // 메서드 종료 시점에 Spring AOP가 DB COMMIT 수행
    }
}

finally 블록에서 lock.isHeldByCurrentThread()를 확인한 뒤 unlock()을 호출한다 — Propagation.REQUIRES_NEW 트랜잭션의 커밋이 끝난 뒤에만 락이 풀린다.
